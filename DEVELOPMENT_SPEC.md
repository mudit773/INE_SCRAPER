# Product Price Tracker - Development Specification

## Instructions for the development model

Build the complete project described in this document in the current repository. Use this file as the source of truth. Inspect the existing repository before editing, preserve unrelated files, and implement the project in small, testable steps.

Use practical free-tier choices and keep the code easy to explain in an interview. Do not introduce microservices, Redis, message queues, user accounts, or other infrastructure that is not required here. Do not invent selectors or product routes before inspecting the target storefront.

The finished repository must contain the frontend, backend, database migration, tests, environment examples, deployment configuration, README, and design note. Run the relevant checks before declaring the project complete.

## Product goal

Build a full-stack web application that searches products on INE's mock storefront, lets a visitor track products, scrapes each tracked product's price and stock every two hours, and displays price history and an honest log of every scrape attempt.

Target store: <https://demo.inelabteamdev.com/>

Only scrape this supplied mock store.

## Required stack

- Frontend: React, TypeScript, Vite; deployable to Vercel.
- Backend: Node.js, Express, TypeScript; deployable to Render.
- Database: Supabase PostgreSQL.
- Scraping: Playwright initially. The storefront's initial HTML is a React shell without product data. During implementation, inspect its network traffic; replace browser work with a lightweight same-store HTTP request only if that path is demonstrably reliable.
- Scheduling: a protected HTTP endpoint called by cron-job.org or an equivalent external scheduler.
- Charts: Recharts or another small React chart library.
- Validation: Zod or an equivalently small validation library.
- Package management: npm workspaces.

## Scope

### Required

1. Search the mock store by partial or full product name.
2. Track a selected product and persist it in Supabase.
3. Scrape tracked products on a fixed two-hour schedule.
4. Extract and validate current price, currency, and stock.
5. Display tracked products with their latest confirmed state.
6. Display price and stock history as a chart and/or table.
7. Display every scrape attempt per product, including retries and failures.
8. Provide a local headed mode so scraping can be watched.
9. Handle delayed content, slow responses, temporary errors, invalid values, selector changes, and process restarts.
10. Include deployment and setup documentation.

### Deliberately out of scope until all required work passes

- Authentication or multiple user accounts.
- Email alerts.
- Configurable schedules.
- Redis, queues, background worker services, and microservices.
- Scraping any site other than the supplied mock store.

## Database design

Create one SQL migration containing the tables, constraints, indexes, and small database functions needed for atomic claiming and successful persistence.

### `tracked_products`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key; generated by PostgreSQL |
| `source_product_id` | `text` | Required and unique |
| `url` | `text` | Required and unique; must belong to the mock-store origin |
| `name` | `text` | Required |
| `image_url` | `text` | Nullable |
| `active` | `boolean` | Required; default `true` |
| `created_at` | `timestamptz` | Required; default `now()` |
| `next_scrape_at` | `timestamptz` | Required; new products are immediately due |
| `lease_token` | `uuid` | Nullable |
| `lease_until` | `timestamptz` | Nullable |

Index `next_scrape_at` for active rows.

### `scrape_attempts`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `product_id` | `uuid` | Required FK to `tracked_products` |
| `run_id` | `uuid` | Required; shared by attempts in one scrape run |
| `attempt_number` | `smallint` | Required; starts at 1 |
| `trigger` | `text` | `scheduled` or `manual` |
| `started_at` | `timestamptz` | Required |
| `finished_at` | `timestamptz` | Nullable while running |
| `status` | `text` | `running`, `success`, `retried`, or `failed` |
| `error_code` | `text` | Nullable |
| `error_message` | `text` | Nullable; safe for dashboard display |
| `duration_ms` | `integer` | Nullable |

Add a unique constraint on `(run_id, attempt_number)` and an index on `(product_id, started_at desc)`.

Status semantics:

- `running`: the attempt started but has not finished.
- `success`: valid data was stored.
- `retried`: this attempt failed and a subsequent attempt actually began.
- `failed`: the final attempt failed and no later attempt began.

### `price_history`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `product_id` | `uuid` | Required FK |
| `attempt_id` | `uuid` | Required unique FK to the successful attempt |
| `price` | `numeric(12,2)` | Required and non-negative |
| `currency` | `text` | Required |
| `in_stock` | `boolean` | Required |
| `observed_at` | `timestamptz` | Required |

Add an index on `(product_id, observed_at desc)`.

Store a successful observation even when the price and stock have not changed. It proves that the scheduled check succeeded.

### Atomic database operations

Implement a small PostgreSQL function that atomically claims due active products by setting an expiring lease. A concurrent cron request must not claim the same product.

Implement another function or transaction that inserts `price_history`, marks the corresponding attempt successful, updates `next_scrape_at`, and clears the lease together. A partial success must not be possible.

Enable RLS on public tables. The browser must not access these tables directly. All application database access goes through the Express backend using a server-only Supabase secret key.

## Scraper behavior

### Store inspection

Before writing final selectors:

1. Open the storefront with Playwright.
2. Inspect product search/listing behavior, product identifiers, product URLs, API/XHR requests, delayed fields, and error behavior.
3. Record the selectors or same-origin API contract in `DESIGN.md`.
4. Prefer a stable same-origin product ID and canonical product URL.

Do not treat initial empty HTML as a scrape failure if the content is still loading.

### Extraction contract

The scraper returns this only after all fields are validated:

```ts
type ScrapedObservation = {
  sourceProductId: string;
  name: string;
  price: number;
  currency: string;
  inStock: boolean;
  observedAt: string;
};
```

Validation rules:

- Confirm the loaded page represents the requested product.
- Price must be finite, non-negative, and parsed from an expected price element or verified response field.
- Currency must be recognized explicitly.
- Stock must be derived from an explicit stock state. Missing stock data is an error, not `false`.
- Empty text, placeholders, loading skeletons, and unrelated numbers are invalid.
- Do not write `price_history` when validation fails.

### Retry strategy

- Maximum three attempts per product run.
- Initial per-attempt deadline: approximately 25 seconds; adjust only after measuring the site.
- Backoff after the first and second failure: approximately 2 and 5 seconds with small random jitter.
- Retry network failures, navigation timeouts, HTTP 429, HTTP 5xx, and delayed required content.
- Respect a reasonable `Retry-After` value within the overall request budget.
- Treat a confirmed 404, invalid product identity, or persistent parser mismatch as a clearly classified failure.
- Before starting a new attempt, mark the prior failed attempt `retried`.
- If all attempts fail, mark the last attempt `failed` and retain the error.

Wait for valid product data rather than using a fixed sleep or relying only on `networkidle`. Use a small set of verified selectors or a verified same-store response shape. Do not fall back to the first currency-looking number on the page.

Initially process one product at a time. Reuse one browser per cron batch and close pages after each product. Keep the batch small enough to complete within the verified scheduler timeout.

### Recovery

- An expired lease makes a product claimable after a crashed process.
- Reconcile abandoned `running` attempts as failed with an interruption error.
- If Supabase cannot be reached, return an error and write a structured server log. Never report persistence success without confirmation.
- Keep diagnostic server logs free of secrets and sensitive headers.

### Headed demonstration

Provide this command or a close equivalent:

```bash
npm run scrape:headed -- --product <tracked-product-id>
```

It must invoke the same production scraper with Playwright headed mode enabled. Log navigation, validation, retries, and the final outcome visibly. If a slow or failed request is simulated for the recording, label it clearly as simulated.

## API contract

All routes begin with `/api` and return JSON.

### Public application routes

| Method | Route | Behavior |
|---|---|---|
| `GET` | `/api/health` | Return backend and database readiness |
| `GET` | `/api/search?q=<name>` | Search store products by partial/full name |
| `POST` | `/api/products` | Track `{ "sourceProductId": "..." }`; resolve product details server-side |
| `GET` | `/api/products` | List active products with latest observation and latest attempt |
| `GET` | `/api/products/:id` | Return one tracked product and latest state |
| `DELETE` | `/api/products/:id` | Set `active=false`; preserve all history |
| `GET` | `/api/products/:id/history?limit=100&before=<timestamp>` | Paginated observations |
| `GET` | `/api/products/:id/attempts?limit=50&before=<timestamp>` | Paginated attempt log |

Tracking a product that already exists should reactivate and return the existing row. A newly tracked product is immediately due.

### Protected routes

| Method | Route | Behavior |
|---|---|---|
| `POST` | `/api/jobs/scrape-due` | Claim and scrape a bounded batch of due products |
| `POST` | `/api/products/:id/scrape` | Run one manual scrape for development/demo |

Require `Authorization: Bearer <CRON_SECRET>` for protected routes. Compare the complete value safely and return `401` on failure.

Use consistent errors:

```json
{
  "error": {
    "code": "STORE_TIMEOUT",
    "message": "The store did not respond in time."
  }
}
```

Validate query strings, UUIDs, body fields, search length, and pagination limits. Accept product IDs from search results rather than arbitrary user-supplied URLs.

## Frontend requirements

Create a clean responsive dashboard with:

- A search box with debouncing and clear loading/error/empty states.
- Search results with a Track action.
- Cards or a compact table for tracked products.
- Latest confirmed price, currency, stock, successful check time, and latest attempt status.
- A visible stale/error state so an old value is not presented as newly verified.
- A product detail view with price history chart/table and scrape-attempt log.
- Attempt rows showing timestamp, attempt number, status, duration, and safe error message.
- An untrack action with a simple confirmation.

The frontend must use the Express API. Do not expose the Supabase secret key or call private tables from browser code. Do not ship fake production data.

Prioritize clarity over visual complexity. Use accessible labels, keyboard-friendly controls, sufficient contrast, and layouts that work on mobile.

## Scheduling and deployment

Deploy the frontend to Vercel and backend to Render. If Playwright remains required, configure Render with a Dockerfile or another supported setup that includes its browser and system dependencies.

Configure the external scheduler to call `POST /api/jobs/scrape-due` every 10 minutes with the bearer secret. The database decides which products are due, so each product is scraped no more frequently than every two hours. Frequent triggers provide retries after cold starts or failed cron requests.

Keep the cron request open until its claimed batch has completed and persistence has finished. Do not return early and continue essential work only in process memory.

Required environment variables:

```dotenv
# Backend
SUPABASE_URL=
SUPABASE_SECRET_KEY=
CRON_SECRET=
FRONTEND_ORIGIN=http://localhost:5173
PORT=3000

# Frontend
VITE_API_BASE_URL=http://localhost:3000/api
```

Use the current Supabase server secret key naming recommended by its dashboard. If only the legacy service-role key is available, document the matching variable name and keep it server-side.

Other deployment requirements:

- Restrict CORS to local development and the deployed frontend origin.
- Restrict all scraper navigation and redirects to `demo.inelabteamdev.com`.
- Add conservative rate limits to search and product mutations.
- Bound search length, page sizes, batch size, and scraper deadlines.
- Add `/api/health` without exposing configuration values.
- Do not rely on Render's filesystem for persistent data.

## Testing requirements

Use a small, meaningful suite. Avoid tests that only repeat implementation details.

Required automated coverage:

1. Price/currency/stock parsing, including invalid and missing values.
2. Delayed valid content.
3. Temporary failure followed by success.
4. Retry exhaustion and final failure logging.
5. Failed validation creates no price-history row.
6. Successful observation and attempt completion are atomic.
7. Concurrent cron requests cannot claim the same product.
8. Expired lease recovery.
9. API input validation and protected-route authentication.
10. One frontend flow covering search, track, and viewing history/logs with mocked API responses.

Use local HTML fixtures or intercepted Playwright responses to test loading, timeout, malformed price, missing stock, and changed selectors deterministically. Do not make the normal automated test suite depend on the live storefront.

Also provide a clearly named optional live smoke-test command. It should perform read-only storefront inspection unless a backend/database test environment is explicitly configured.

Run and report:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

## Acceptance criteria

The project is complete only when all of the following are true:

- A partial-name search returns real mock-store products.
- A selected product can be tracked and survives process restarts.
- A successful scrape stores a validated observation and successful attempt.
- A failed or retried scrape is visible in the product's attempt log.
- Invalid, empty, or mismatched product data never creates price history.
- Overlapping cron requests cannot process the same product concurrently.
- Products become due every two hours and can recover from an expired lease.
- The dashboard clearly distinguishes current success, stale data, and failures.
- The production frontend and backend builds succeed.
- The headed command visibly runs the production scraper.
- Setup, deployment, scheduling, and design decisions are documented.

## Five mistakes to guard against

1. Reading a placeholder or skeleton price before asynchronous content finishes.
2. Converting a missing price to zero or missing stock to out-of-stock.
3. Recording only the final outcome and hiding failed retry attempts.
4. Depending on `setInterval`, process memory, or background work after an HTTP response.
5. Allowing overlapping cron calls or partially saving a successful result.
